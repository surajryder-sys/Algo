**V5-Sentinel** (`v5_sentinel/`) is the current live XAUUSD bot lineage, "V5S" prefix everywhere (comments, env vars). As of 2026-09-18 the user is starting **V6-Sentinel** ("V6S") -- a deliberate rebuild, porting only verified-necessary logic across one component at a time after discussion, dropping what's not needed. This memory is the saved reference map for that migration. See [[feedback_algo_trading_collab]] for working style, [[project_v4_xauusd_architecture]] for the lineage before this one.

## Confirmed design decisions worth carrying into V6S as-is

- **M15 Primary Structure** gates RM-STR/RM-ICT's triggers: agree -> ST1F (M1 Supertrend) or M3F (M3 ATR-dual flip), either sufficient; disagree -> ST3F (M3 Supertrend) or M5F (M5 ATR-dual flip), whichever first. CISD triggers (M3CD/M5CD) are the one exception -- deliberately ungated, fire independently of M15.
- **CISD SL basis**: nearest active swing low/high (frozen at confirmation), NOT the origin candle's own open -- too premature/easy to stop-hunt.
- **RM-ICT zone eligibility**: exists + retested (genuine price retest, not just "untested") + not traded + not overlapping an already-traded zone (60% threshold). "Untested/virgin" means "not yet traded," NOT "price hasn't touched it" -- that distinction caused a real bug, see below.
- **TM-ICT Rule 3** (3F/ST3F): no proximity requirement by design (catches zones too far for Rule 1/2), but capped at 50 candles of that component's own timeframe -- an unbounded-age Rule 3 fired a real 12-day-old zone.
- **ICT Guard**: sticky once blocked (a zone that's ever blocked stays blocked until genuinely invalidated, never re-clears from price just drifting away). Notification (log/alert) is deduped to once per zone per process lifetime, not every cycle it stays blocked.
- **Exit Manager**: fully symmetric across all 4 components (not paired) -- any fresh fill squares off every other component's opposite position. Reacts only to `entry_filled`, never `entry_decision_only`.
- **Block retention (2026-09-17 architecture change)**: mirror only what's currently on the real chart, not permanent accumulation. Any zone the scraper stops reporting gets pruned, even one holding an active sticky guard block. Already-traded eligibility history persists independently (separate store, not a live reference).
- **Zone timestamp validation**: a `start_time` is only ever a valid candle-open for ONE timeframe's own bar grid. TradingView's own vendor grid has PER-TIMEFRAME offsets that differ from MT5's own broker feed (confirmed: H4 runs a consistent +1hr offset vs MT5; M5/M15/M30/H1 align to 0) -- derive offsets statistically from the zone data itself, never assume MT5's own rates are the right reference for TradingView-sourced data.

## Every real bug found and fixed (the actual lessons for V6S -- design around these from day one, don't rediscover them)

1. **Bridge tie-breaker v1** compared the bridge's own bundled `structure` field instead of raw trail values -- caused a false-positive REFRESH trade. Fixed: always use raw `line1`/`line2` trail values through the same geometric test, never a pre-bundled "structure" verdict from elsewhere.
2. **ICT Guard not sticky** -- a block that should stay blocked cleared just because price drifted a few points, then fired on pure noise. Fixed: sticky-until-invalidated.
3. **TM-STR initial SL for ATR_STRUCTURE source** was a live-drifting bridge read instead of frozen-at-the-flip-bar -- SL matched the pre-flip line, not post-flip. Fixed: freeze via `tracker.event_far_near()`.
4. **RM-ICT / TM-ICT duplicate trades on the same real zone** re-identified under a fresh `zone_id` after a scraper "flicker." Fixed: `overlaps_traded()` 60%-overlap geometric guard.
5. **RM-ICT zone eligibility redesign** conflated two different things: "not yet traded" (eligibility) vs "price hasn't retested it" (a separate, necessary gate) -- dropping retest entirely let a trade fire off a zone 11+ points from live price. Fixed: retest requirement reinstated alongside traded-eligibility.
6. **Redundant-signal Telegram spam**: RM-ICT's own eligibility redesign let ONE trigger match dozens of untested zones at once, each independently alerting -- 78 messages from one real event. Fixed: aggregate to one alert per component per cycle; same fix needed (and applied) for ICT Guard's own block notifications and TM-STR's own `m3_signal` logging, all of which had the identical "re-logs every cycle, not once per event" spam pattern.
7. **TM-STR Trigger 1 ("FRESH") had no bar-close gate** -- compared two STANDING timestamps (`m3.event_time > parent.event_time`), which stays true indefinitely once true, not just "on the flip candle" as documented. A real trade fired 47 minutes after its own flip, having sat ICT-Guard-blocked the whole time. Fixed: added genuine bar-close freshness check, source-specific (Supertrend vs ATR_STRUCTURE each need their own one-shot check).
8. **Cross-timeframe zone misattribution** (the big one): tv_scraper's own Data Window scroll-and-capture (16 steps, ~3.4s) can outlast Pine's own recalculation lag after a pane-focus switch -- the SAME real zone got seeded under M3, H4, H1, AND M15 simultaneously over a ~2hr window, each with a start_time that's provably invalid for its claimed timeframe. Root cause not fully closed (a 1.5s pre-scroll wait was tried, unclear if sufficient) -- but TWO independent defensive backstops now catch it regardless of cause: (a) reject any zone whose start_time isn't a valid candle-open for its own claimed timeframe (derived per-timeframe offsets statistically, since MT5's own grid ≠ TradingView's own grid for at least H4), (b) reject an exact duplicate of an already-known zone appearing under a different timeframe. Audited the live Block against this and found 53 confirmed-false zones, 37 already traded -- this had been silently causing bad trades for a while before being caught.
9. **Block/Store permanent accumulation**: `nlb_nsb_block.py`/`ict_ob_block.py` both followed "seed once, keep forever" with no re-sync against the scraper's own current view, even though tv_scraper's own `ZoneStore` already genuinely deletes on 2-poll-confirmed mitigation. Real impact: 232 zones held vs a handful ever actually on chart at once. Fixed with pruning added to both.
10. **Pine's own `max_bars_back(time, 5000)` hard ceiling**: a zone older than 5000 bars on a given timeframe can NEVER get a confirmed `FormedMinutesRef` on that timeframe -- structural TradingView platform limit, not fixable Pine-side (confirmed rejected at compile time for any larger value). `RetestedMinutesRef` is a SEPARATE, independent offset (from the retest bar, not the formation bar) and can still resolve even when formed can't. Current V5S behavior: such zones are never seeded downstream at all (already matches "just ignore" -- confirmed as acceptable behavior with the user, the tradeoff being those zones can never become trade-eligible even if genuinely retested).
11. Several **"Windows App Execution Alias" / orphaned Brave / CDP port conflicts** around tv_scraper restarts -- confirmed harmless duplicate-process artifacts vs genuine CDP-lock conflicts (the latter needs killing ALL Brave processes before a clean relaunch, not just the Python wrapper).

## Operational conventions (all still apply)

Own MT5 terminal connection per component, own magic number, own state files, gitignored. `*_ENABLE_TRADING=false` default, never restart live trading without the user's explicit go-ahead each cycle. Standard workflow: verify against real data -> implement -> unit test (mocked, controlled cases) -> dry-run against live data -> restart only affected processes -> background health-check (heartbeat freshness, 6-8 checks over ~40s) -> commit -> push -> pull -> report. Multiple Claude Code sessions work this repo concurrently -- `git status`/`git diff` before committing to avoid clobbering another session's in-progress uncommitted work (confirmed live 2026-09-16/17: a `CISD_AlgoAlpha.mq5` change from another session sat uncommitted for a full day while this session worked alongside it).

**How to apply**: read this in full before starting any V6S component port -- it's the actual, verified state of V5S as of 2026-09-18, not a summary from early design discussion. When porting a component, check its own bug history above first; several of these (misattribution, permanent accumulation, sticky-notification spam, bar-close-gating) are generic patterns likely to recur in V6S's own equivalents if not designed around from the start.
